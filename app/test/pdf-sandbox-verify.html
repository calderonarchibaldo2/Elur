PDF sandbox verification harness

Reproduces Elur's paintContent PDF path exactly — URL.createObjectURL(new Blob([bytes],{type:"application/pdf"})) in an <iframe> — across three sandbox settings, side by side. Open this file inside the Elur app's WebView (or Safari — same WebKit engine). The only question each row answers: does the PDF still render, and does active content stay inert?

Columns:   no sandbox = current shipped baseline  ·  sandbox="" = the proposed hardening fix  ·  sandbox="allow-same-origin" = the audit's fallback.   A column passes render if you can read the PDF text in it.

1 · Normal PDF — the render test (THE blocker)

Clean PDF, no scripts. If a column is blank/grey, that sandbox setting breaks rendering in this engine (WebKit bug 118859) and is unusable as-is.

Look at all three: which columns show the text? The fix is only viable if sandbox="" renders.

2 · Embedded-JS PDF — the execution test

Carries an OpenAction /JavaScript that fires app.alert('XSS-FIRED…') on open. A safe viewer runs nothing.

Did any alert/dialog appear when the page loaded? If no dialog popped → JS did not execute (safe). WebKit's native viewer never runs PDF JS; this confirms it.

3 · External-ref PDF — the phone-home test

On open it attempts submitForm, launchURL, and Net.HTTP.request to elur-pdf-probe.example.invalid, plus a clickable URI link.

Open the Network tab, then reload. Zero requests to elur-pdf-probe.example.invalid = no phone-home (safe). This domain is intentionally unresolvable, so any attempt shows as a failed request.

4 · pdf.js canvas — THE FIX (what the app now ships)

Same three PDFs, rendered the way paintContent renders them now: pure-JS rasterization to a <canvas>, no native viewer, no sandbox dependency. Expected: all three show their text, no alert fires, and the network sentinel below stays at 0.

All three render via pdf.js regardless of engine, no dialog appears, and the sentinel reads 0 → the fix gives display-only preview with no script execution and no phone-home.

How to run this (2 minutes)

  1. Open this .html inside the Elur app (drag into its window / load via a route) so it runs in the real WKWebView. Safari is an acceptable proxy — same engine.
  2. Row 1: note which of the three columns actually show text. That decides whether sandbox="" is shippable.
  3. Row 2: confirm no alert dialog appeared on load.
  4. Row 3: open Web Inspector → Network, reload, filter for probe. Confirm zero outbound attempts.

Heads-up from the research: WebKit historically blanks PDFs inside sandbox iframes (bug 118859) — and allow-same-origin doesn't re-enable them. If Row 1's sandbox="" column is blank, the iframe-sandbox approach is a dead end and the robust fix is to render the inline preview with pdf.js (already vendored for text extraction) to a canvas — that runs no PDF JS and makes no network requests by construction, independent of WebKit quirks.
